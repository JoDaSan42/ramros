# RAMROS 1.4.0 — Erweiterungen & Fixes (Fünf Increments)

**Datum:** 2026-11-13
**Status:** Approved — scope/order approved by user 2026-11-13; drei offene Fragen im
Verlauf entschieden (B: Play-Button bleibt direkt; C1: RViz/rqt starten prompt-frei,
build/bag unverändert; C3: alle ros2-Execs zentral geroutet + Multi-Domain-Live-View

**Ursprung:** Brainstorming 2026-11-13. Acht neue Feature-Ideen wurden bewertet (Einarbeitung, Aufwand, Risiko, Nutzen); dazu kommt die approved, aber noch nicht umgesetzte Spec für strukturierte Message-Eingabe (2026-10-13), die für Release 1.3.0 ausdrücklich „deferred to next increment" wurde.

## Intent und Warum

Nach 1.3.2 ist der Code-Debt des Architektur-Reviews vollständig abgebaut (alle 24
Findings verifiziert erledigt), 231 Unit- und 272 Integrationstests sind grün.
Dieser Release-Zyklus vertieft die beiden täglichen Workflows — Nodes mit Optionen
starten und die Live-View — und räumt wiederkehrende Reibung weg (Workspace-Prompts,
ROS-Pfad, Domain-ID). Die strukturierte Message-Eingabe wird wie zugesagt Teil
dieses Zyklus.

## Increment A — Live-View Lazy Loading

### Problem (verifiziert im Code)

Jeder Auto-Refresh-Tick (Default 5 s) ruft in
`LiveTreeProvider.getChildren` für **jeden** Node `ros2 node info <node>` und für
**jedes** Topic `ros2 topic info --verbose` auf — sequenziell, je 5 s Timeout
(`ros2-cli-service.ts:188/279`). Bei 20 Nodes + 30 Topics sind das ~52 Subprozesse
pro Tick. Die 1.3.2-Optimierung betrifft nur die Parameter-Liste, nicht Node-/Topic-Info.

### Design

- Refresh-Tick lädt nur noch `ros2 node list` + `ros2 topic list` (**2 Calls pro Tick, O(1)**).
- `LiveNodeItem`/`LiveTopicItem` werden nur mit dem Namen konstruiert;
  die Info (Pub/Sub, Typ, Services) lädt erst in `getChildren()` beim Aufklappen
  und wird am Item gecacht. VSCode ruft `getChildren` nur für aufgeklappte Items auf —
  die Call-Anzahl skaliert mit dem, was der Nutzer aufklappt, nicht mit der Systemgröße.
- **Refresh-Mechanik (Builder-Check-Fund):** Items werden pro Tick neu konstruiert,
  eine reine `description`-Mutation re-rendert nicht. Der Provider besitzt den
  Info-Fetch: er hält einen Info-Cache (name → info, TTL bis zum nächsten Tick) und
  feuert `onDidChangeTreeData` **pro Element** nur für jene Items, deren
  Beschreibung sich nach dem Aufklappen geändert hat — kein Full-Fire (Loop/Flicker).
- Vor dem ersten Aufklappen zeigt die Description `running` (Nodes) bzw. leer
  (Topics); nach dem Fetch die bekannte Zusammenfassung (`3 pub / 2 sub`,
  Message-Typ).
- Nach einem Refresh-Tick holt ein aufgeklapptes Item beim nächsten `getChildren`
  frische Info (Cache TTL = Tick-Intervall) — Daten bleiben aktuell.
- **System-Topic-Filter bleibt auf den Zählern wirksam** (1.3.2-Semantik): der
  Filter (heute in `LiveTreeProvider.getNodeInfo`, live-tree-provider.ts:211-217)
  wandert mit in den Provider-Fetch, damit `3 pub / 2 sub` weiterhin ohne
  `/rosout` & Co. zählt.
- Command-Flows (Publish, Service Call) lösen den Typ weiterhin selbst beim Command
  auf (bestehender Fallback-Pfad) — davon ist die Lazy-Änderung nicht betroffen.

### Alternativen (verworfen)

- **Parallelisierte Info-Fetches**: bleibt O(N) Subprozesse pro Tick, belastet den
  ros2-Daemon; löst das Grundproblem nicht.
- **DDS-Introspection/`ros2 daemon`-API direkt**: Forschungsprojekt, keine stabile API.

### Tests

- Integration (vscode-Mock, gezählte CLI-Calls): ein Tick erzeugt genau 2 Calls,
  unabhängig von Node-/Topic-Anzahl — **und** der Element-Fire nach einem
  Fetch triggert keinen erneuten Info-Fetch (Loop-Schutz).
- Item.getChildren lädt Info einmal beim Aufklappen; Description wechselt von
  `running` zur Zusammenfassung.
- **System-Topic-Filter**: gezählte Pub/Sub-Description schließt `/rosout` &
  Co. weiterhin aus (1.3.2-Semantik).
- **Parameter-Cache unberührt**: wiederholtes Aufklappen eines Nodes re-fetched
  die Parameterliste nicht (1.3.2-Guard, `NodeParametersItem`).
- Aufgeklapptes Item zeigt nach einem Tick frische Werte (Cache-TTL).

## Increment B — Node-Start-Optionen (Parameter, Name, Remaps)

### Ist-Status (verifiziert)

`ramros.runNode` (extension.ts:658) baut fix `ros2 run <pkg> <exe>` (+ source).
Vorhanden und wiederverwendbar:

- **Statische Parameter-Extraktion** für Python (`declare_parameter`-Regex,
  package-discovery.ts:718) **und** C++ (Zeile 891) mit Name/Type/defaultValue
  (`ParameterInfo`, landet in `NodeInfo.parameters`).
- **`ParameterCoercer`** (core, pure) mit `validate(value, type)` — die strikte
  Typprüfung aus 1.3.0 (ints vs. doubles, Arrays, bools).
- **`PackageFormValidator.validateNodeNameInput`** für Namensvalidierung.
- Shell-Quoting-Muster aus `ros2 param set` (1.3.1-Fix).

### Design (Dialogfluss, kein Webview)

**Invocation-abhängig (User-Entscheidung 2026-11-13):**
- **Play-Button im Tree / Node-Klick: startet direkt** wie heute — null Extra-Keystroke, der Anti-Goal-Schnellweg bleibt exakt erhalten.
- **Command-Palette** (`ramros.runNode` ohne TreeItem): QuickPick **„Start" / „Start with options…"** — Enter startet sofort, „Start with options…" führt durch den Wizard. Esc bricht ab.
   - **Parameter**: Multi-Select-QuickPick der statisch gefundenen Parameter
     (Anzeige `name : type = default`) + „Add custom parameter…" + „Skip".
     Je gewähltem Parameter eine InputBox, vorbelegt mit dem DefaultValue,
     `validateInput = ParameterCoercer.validate(value, type)`.
     Custom-Parameter: Name-InputBox, dann Typ-Auswahl
     (string/int/float/bool/string[]/int[]/float[]/bool[]) — Arrays als
     Komma-Liste, `ParameterCoercer` validiert beide; kein Type-Inferencing
     (explizit wählen ist im Dialog verlässlicher).
   - **Node-Name**: InputBox, Default = aktueller Name. Der vorbelegte Wert
     bleibt unverändert → Node läuft unter dem heutigen Namen (leer löschen
     heißt „unverändert", nicht „Fehler"; `validateNodeNameInput` greift nur
     bei geändertem Wert).
   - **Remaps**: Schleife („Add remap?" yes/no), je Remap zwei InputBoxes
     (from, to). Leichte Validierung: nicht-leer, keine Leerzeichen, Hinweis
     bei fehlendem führendem `/` (Warnung, kein Block).
   - **Esc jederzeit**: bricht den kompletten Wizard ab, es startet nichts
     („alles oder nichts" — kein Teilstart mit Halboptionen).
4. Kommando-Aufbau:
   `ros2 run <pkg> <exe> --ros-args -p <name>:=<value> … -r <from>:=<to> … -r __node:=<name>`
   (Parameter zuerst, dann Remaps, `__node` zuletzt — festgelegte Reihenfolge
   als Testkonvention; ROS selbst wertet die Reihenfolge innerhalb von
   `--ros-args` nicht semantisch aus).

### Neues Core-Modul

`src/core/run-args-builder.ts` (pure, ohne vscode-Import):
Eingabe `{ params: [{name, value, type?}], remaps: [{from, to}], nodeName? }` →
`--ros-args …`-String. Typbewusste Formatierung: Strings single-quoted (mit
Escaping), bools als `true`/`false`, Zahlen roh, Arrays als `[a,b,c]`.
Wiederverwendet `ParameterCoercer` für die Prompt-Validierung; das Modul selbst
formatiert nur noch die finalen Argumente.

### Alternativen (verworfen)

- **Webview-Formular sofort**: das Webview-Muster entsteht erst in Increment D;
  B sollte klein und ohne neue Infrastruktur shippen. Portierung von B auf
  D's Formular ist ein möglicher Folgewechsel, kein Ziel dieses Zyklus.
- **Optionsdialog immer zeigen**: Anti-Goal (Reibung im Standardfall).
- **Run-Optionen pro Node persistieren** (`ramros.json` runProfiles): bewusst
  Non-Goal in diesem Zyklus, möglicher Follow-up.

### Tests

- Unit (`run-args-builder`): Quoting (Leerzeichen, Quotes, leerer String),
  bool/number/array-Formatierung, `__node`-Reihenfolge, keine Argumente → leerer String.
- Integration (vscode-Mock): Wizard-Folge Parameter → Name → Remaps per Palette;
  Play-Button-Invocation startet **ohne** QuickPick direkt (invocation source
  aus dem TreeItem-Argument ableitbar); invalid Parameterwert blockiert;
  Wizard-Esc startet nichts; Name vorbelegt-unverändert erzeugt kein `__node`-Remap;
  finaler zusammengesetzter Terminal-Befehl am `executeInNewTerminal`-Seam
  (Quoting + Reihenfolge real).

## Increment C — Einstellungs-Trio

### C1 — RViz2/rqt starten ohne Workspace-Auswahl (User-Entscheidung 2026-11-13)

**Antwort auf „ist der Workspace für RViz/rqt überhaupt nötig?": Für den Start
selbst nein — aber das Overlay-Sourcing bringt eigene Messages/Interfaces ins
Tool (eigene Topic-Typen sind sonst in RViz2 nicht darstellbar).** Deshalb:

- **Single-Workspace:** RViz2/rqt_graph starten direkt mit Overlay-Sourcing —
  kein Prompt, so wie der Nutzer es erwartet („diese Tools laufen doch
  unabhängig"). `pickWorkspace()` wird für diese Commands gar nicht mehr
  benutzt; stattdessen: erster Workspace, bei Mehrdeutigkeit einziges
  Overlay-Workspace.
- **Multi-Workspace:** QuickPick nur dann — Overlay-Kontext ist hier real
  mehrdeutig. Das zuletzt gewählte Overlay-Workspace wird pro Fenster
  (`context.workspaceState`) gemerkt und im QuickPick **oben mit „(last used)"**
  gelistet (Ein Enter genügt; kein silent reuse).
- **„Ohne Sourcing"-Option** im Multi-Workspace-Pick (rohes Tool, wenn Overlay
  kontraproduktiv ist).
- `rqt_bag` bleibt bei seiner heutigen Kontext-Pfad-Auflösung
  (`resolveWorkspaceForPath`) und bekommt dieselbe Merkung nur in seinem
  Fallback-Prompt.
- `colcon build` / bag record/playback behalten `pickWorkspace()` unverändert
  (User: „bei colcon build ist das was anderes").

### C2 — ROS-Pfad-Setting

`RosEnvironmentService` hat `rosRoot = '/opt/ros'` hartcodiert
(ros-environment.ts:15) — das Modul ist vscode-frei (nur fs/path).

- Neues Setting `ramros.ros.rosRoot` (string, Default `/opt/ros`).
- `RosEnvironmentService` bekommt den Root per Konstruktor injiziert (Default
  bleibt `/opt/ros`); extension.ts liest das Setting bei activate.
- Bei Setting-Änderung **`setRosRoot()` auf der bestehenden Instanz** (der
  Service wird von `WorkspaceDetector`/`PackageCreator` per Closure gehalten —
  Neubau der Instanz würde nichts aktualisieren; Builder-Check-Fund) +
  Invalidation der davon abhängigen Cache-Einträge + Tree-Refresh.
- **Löst Windows nicht** (siehe Non-Goals): Detection sucht `setup.bash`.

### C3 — ROS_DOMAIN_ID mit Multi-Domain-Live-View (User-Entscheidung 2026-11-13)

**User-Wunsch:** nicht eine feste Domain, sondern mehrere Domains wählbar —
gerade im Live-View will man verschiedene Domains untersuchen („wer ist auf
Domain 2 noch so aktiv?").

**Teil 1 — Zentrale env-Injektion (User: „alles durch die env-injection"):**

Der Builder-Check ergab, dass ros2-Execs an vielen Stellen vorbeilaufen
(~10 direkte `execAsync`-Aufrufe in `Ros2CliService` jenseits von
`executeCommand`, 4 weitere in `extension.ts`: `executeCommandAndGetOutput`,
`showInterfaceDefinition`, `runHealthCheck`). Mit Teilabdeckung würde die
Live-View stille falsche/leere Daten zeigen — das Anti-Goal. Deshalb:

- **Alle ros2-Aufrufe werden durch `Ros2CliService` geroutet** (Refactor:
  die 4 `execAsync`-Stellen in extension.ts wandern in Service-Methoden).
- `Ros2CliService` injiziert bei jedem exec `env: { ...process.env,
  ROS_DOMAIN_ID: id }`, wenn eine Domain gesetzt ist; `setDomainId(id |
  undefined)` vom extension.ts aus (activate + Setting-Change).
- `TerminalManager.executeInNewTerminal` stellt bei gesetzter Domain
  `export ROS_DOMAIN_ID=<id> && ` vor (Terminals sind bash).
- Bag-Session, Live-View, Wizard-Validierungen erben das automatisch.

**Teil 2 — Live-View pro Domain-Gruppe:**

- Neues Setting `ramros.liveView.domainIds` (array of number, Default `[]` =
  nur die Umgebung). Plus optionales `ramros.ros.domainId` (number, unset =
  Umgebung, wie oben) als Terminal/exec-Default.
- Der Live-View-Ordner **Nodes** listet pro konfigurierter Domain eine
  **Gruppe „Nodes (domain N)"** mit eigenen LiveNodeItems; Topics analog.
  `Ros2CliService` bekommt `getActiveNodesForDomain(id)` /
  `getActiveTopicsForDomain(id)` (env mit `ROS_DOMAIN_ID: String(id)` pro
  Call — unabhängig vom global gesetzten Default).
- Domain-Gruppen sind aufklappbar; Details laden wie in Increment A lazy.
- Kein Domain-Eingabefeld zur Laufzeit (QuickPick/Prompt): Domains kommen aus
  dem Setting — deklarativ, hot-reload via `onDidChangeConfiguration`
  (Muster existiert). Ein Laufzeit-QuickPick wäre pro Refresh-Tick unklar
  (welche Domain gilt wann?) und wird nicht gebaut.
- **Sichtbarkeit:** Ist `ramros.ros.domainId` gesetzt, zeigt der „ROS2
  Tools"-Root-Knoten `ROS_DOMAIN_ID=<id>` in der Description (Anti-Goal-Schutz
  gegen stille Verwirrung). Domain-Gruppen im Live-View sind selbst-beschriftet.

### Tests

- **C1:** Single-Workspace: rviz2-Command startet ohne jeden Prompt und mit
  Overlay-Source; Multi-Workspace: QuickPick mit „(last used)" oben;
  „ohne Sourcing"-Option baut Befehl ohne `source`; build/bag-Prompts
  unverändert (Regressionsschutz).
- **C2:** `setRosRoot()` ändert nachfolgende Detection-Ergebnisse; abhängige
  Cache-Einträge werden invalidiert; Setting-Change triggert Refresh.
- **C3 (Injektion):** `Ros2CliService`-Methoden (auch die ehemals in
  extension.ts lebenden) führen exec mit `env.ROS_DOMAIN_ID` aus, wenn gesetzt;
  `unset` → env unverändert; Terminal-Zeile enthält `export`-Präfix nur bei
  gesetzter Domain; Tools-Root-Description zeigt die Domain.
- **C3 (Multi-Domain):** Live-View baut pro `domainIds`-Eintrag eine beschriftete
  Gruppe; Gruppen-Calls tragen `ROS_DOMAIN_ID: String(id)`; hot-reload der
  Setting-Änderung baut Gruppen neu; leere Liste → keine Gruppen (Ist-Zustand).

## Increment D — Strukturierte Message-Eingabe

Implementiert die **approved Spec**
`docs/superpowers/specs/2026-10-13-structured-message-input-design.md`
wortwörtlich — Intent, Goals/Non-Goals/Anti-Goals, Abläufe, Struktur-Loader,
Array-Regeln, Panel-Semantik, Architekturhinweise und Constraints stehen dort
und werden hier nicht dupliziert.

Sequenz-Note: D kommt nach A–C, damit zuerst das Webview-unabhängige Fundament
sitzt und der Live-View schnell ist, bevor das erste Webview-Pattern gebaut wird.
Neue Module laut Spec: `src/core/interface-parser.ts` (+ rekursiver Loader),
Serialisierung; Panel als Einzelfile-HTML mit Inline-JS/CSS, CSP mit Nonce.

**Tests (Ergänzung zum globalen Constraint — die Spec schreibt keine vor):**

- Unit (`interface-parser`): verschachtelte Typen, Konstanten (weglassen vs.
  read-only), Arrays fix (≤16 → Einzelfelder, >16 → Komma-Feld) und variabel
  (Primitive → Komma-Feld, Nicht-Primitive → JSON-Freitext), `\,`-Escaping.
- Unit (Serialisierung): Werte-Objekt → YAML (`topic pub`) / JSON (`service
  call`), inkl. Escape-Runden.
- Integration: Top-Level-`interface show`-Fehler → Fallback auf Raw-Input-Box
  (nichts wird schlechter); partial failure → nur Teilbaum als Freitext;
  Session-Cache verhindert Sub-Process-Kaskade beim zweiten Öffnen; Panel bleibt
  nach Publish/Call offen mit erhaltenen Werten.

## Increment E — Workspace-Vollständigkeits-Analyse

### Design

Command **„Analyze Workspace Completeness"** (Palette + Kontextmenü auf dem
Workspace-Knoten). Erzeugt einen **Read-only-Report** (etabliertes Muster:
`ramros-doc-provider`, wie `ros2 doctor`/Interface-Definition), gruppiert nach
Paket, mit Severity und file:line wo möglich.

Checks:

1. **Deklarierte vs. genutzte Dependencies** (package.xml ↔ Code):
   Python-`import X`/`from X.<sub> import` und C++-`#include <X/…>` werden auf
   ROS-Pakete gemappt (Heuristik: `X.msg`/`X.srv` → `X`, Validierung gegen die
   gecachte `ros2 pkg list`). Fehlende Einträge = **Warning**. Imports, die sich
   keinem ROS-Paket zuordnen lassen (pip, stdlib, relative), landen unter
   „unknown, skipped".
2. **Entry-Points vs. Node-Dateien** (ament_python): Node-Datei ohne
   `console_scripts`-Eintrag in setup.py = **Error** (genau der
   „hineinkopierten Python-File"-Fall); Entry-Point ohne existierendes Modul =
   **Error** (umgekehrt).
3. **rosidl-Registrierung** (ament_cmake, best effort): msg/srv/action-Dateien im
   Paket, die nicht in den `rosidl_generate_interfaces`-Aufrufen der
   CMakeLists.txt stehen = **Error**. Regex-Parsing wie in `BuildFilePatcher`/
   package-creator etabliert.
4. **Unbenutzte Dependencies**: package.xml-Eintrag ohne gefundene Nutzung =
   **Info**.

Neues Core-Modul `src/core/workspace-analyzer.ts` (pure; fs-Zugriff und
Paketliste injiziert) → unit-testbar. Report-Renderer separat.

### Tests

- Unit (Fixtures unter `test-fixtures/`): je Check Positiv- und Negativ-Fälle —
  fehlende package.xml-Dependency, unregistrierter Python-Node (der
  „hineinkopierte File"-Fall), Entry-Point ohne Modul, nicht in
  `rosidl_generate_interfaces` gelistete msg, unbenutzte Dependency; dazu
  „unknown, skipped"-Klassifikation für pip/stdlib-Imports und Severity-Mapping.
- Integration: Command erzeugt Read-only-Report-Dokument mit gruppierten
  Findings; Workspace ohne Befunde → leerer Report mit Hinweiszeile.

### Alternativen (verworfen)

- **Problems-Panel-Diagnostics**: schwerere Integration (DiagnosticCollection,
  Match-Mapping); als Non-Goal für diesen Zyklus, möglicher Follow-up.
- **On-Scan-Integration** (Analyse bei jedem Tree-Refresh): zu teuer und nervig;
  bewusst expliziter Command.

## Constraints (ganzer Zyklus)

- Keine neuen npm-Dependencies; nur vscode-API und Node-Builtins.
- Nach jedem Task: `npm run lint`, `npm run typecheck`, `test:unit`,
  `test:integration` grün (Baseline: 231 Unit / 272 Integration).
- User-facing Strings Englisch, Code-Kommentare Englisch; Docs/Specs wie hier Deutsch
  (Konvention aus 2026-10-13-Spec).
- Conventional Commits; `package.json`-Version bleibt 1.3.2 bis zum Release-Task
  (1.4.0 am Ende des Zyklus, mit Smoke-Checkliste wie 1.3.0).
- Bestehende Muster: `Ros2CliService`-Singleton, pure command-builders in `src/core/`,
  read-only-Doc-Provider, `ParameterCoercer`-Validierung, `PackageFormValidator`.

## Non-Goals (dieser Zyklus)

- **Windows-Support** (eigenes künftiges Milestone; Antwort auf die Frage: das
  ROS-Pfad-Setting löst das **nicht** — Blocker sind `setup.bash` vs. `setup.bat`,
  POSIX-Quoting, `source &&`-Verkettungen, cmd.exe statt bash in der gesamten
  Ausführungsschicht).
- Problems-Panel-Integration der Workspace-Analyse.
- Persistierung von Run-Optionen pro Node (`ramros.json` runProfiles) — Follow-up-Kandidat.
- Domain-Wechsel zur Laufzeit per Prompt (Live-Domain-Gruppen kommen deklarativ
  aus `ramros.liveView.domainIds`; ein Runtime-QuickPick wäre pro Refresh-Tick
  mehrdeutig).
- Pro-Workspace-Domain-IDs (Domain-Einstellungen sind global).

## Anti-Goals

- Live-View darf beim ersten Rendern nicht langsamer werden als heute.
- Play-Button/Node-Klick im Tree behält den Null-Extra-Keystroke-Direktstart —
  kein Dialog davor (QuickPick nur per Palette).
- Keine stille Environment-Divergenz: gesetzte `ramros.ros.domainId` muss in der
  UI sichtbar sein; Domain-Gruppen im Live-View sind selbst-beschriftet.

## Was dem Builder überlassen bleibt

- Exakte Prompt-Formulierungen, Loading-Placeholder-Verhalten, Fehlertexte.
- Heuristik-Tuning des Analyzers (Import→Paket-Alias-Tabelle, report formatting).
- `ramros.ros.domainId`-Semantik im Detail: „unset = Umgebung unverändert"
  (number-Setting, `undefined` → keine Injektion), konsistent dokumentiert.
- Per-Element-Fire-Mechanik in A (Provider-Info-Cache vs. Item-getChildren-Fetch
  — Design gibt das Ziel vor, die vscode-API-gerechte Umsetzung wählt der
  Builder; Loop-Schutz-Test ist verpflichtend).
- Alle Webview-Details von D gemäß approved Spec.
